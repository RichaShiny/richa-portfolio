Charge Key Classification

A desktop application and multi-stage ML pipeline for standardizing criminal charge codes across jurisdictions, with explicit confidence checks and human review.

CUNY Institute for State and Local GovernanceResearch Data Scientist · May 2026–Present

The idea

Standardize the charge, preserve the uncertainty.

Charge codes and descriptions vary across jurisdictions and reporting years. An unfamiliar code may refer to a known concept, while similar wording can conceal meaningful differences. Missing descriptions, abbreviations, and inconsistent schemas make simple lookup tables insufficient.

At the CUNY Institute for State and Local Governance (ISLG), I work on a desktop classification application that maps new diagnostic charges to existing standardized charge keys. The aim is to reduce repetitive matching while keeping ambiguous cases available for subject-matter review.

Application structure

A desktop interface around a reusable classification pipeline.

The application separates the user interface from the matching engine. A Tkinter desktop layer handles jurisdiction and year selection, input and output locations, classification settings, progress, and errors. The pipeline handles loading, normalization, reference construction, matching, and output generation.

  • Shared classification behavior is packaged for Mac and Windows, with platform-specific application builds.
  • The pipeline runs separately from the main GUI thread so the interface stays responsive.
  • A diagnostic-upload edition accepts a CSV or Excel file and uses bundled, frozen 2021–2025 references for the 16 configured jurisdictions. It supports offline classification and a human-review queue.

This structure lets the operational interface evolve while keeping exploratory analysis and validation work separate.

Data workflows

Two input paths, one standardized reference vocabulary.

Jail workflow. Historical jail charge keys from multiple years are combined into a jurisdiction-specific reference. New diagnostic records are checked for unresolved charges and matched against that history. Combining years increases coverage and can recover descriptions absent from an individual file.

Court workflow. Where historical court charge keys are unavailable, court diagnostic charges use the existing jail charge-key reference. This differs from assuming a separate historical court reference exists.

Completely unseen jurisdictions are a further extension. Their terminology and coding conventions need conservative cross-jurisdiction matching and human validation rather than being treated as equivalent to a configured site.

Pipeline diagram

Use the simplest sufficient evidence first.

Matching logic

Escalate flexibility only when direct evidence is insufficient.

  • Exact matching: reuse a supported historical relationship before invoking more flexible methods.
  • Fuzzy matching: account for abbreviations and small textual differences that preserve the underlying description.
  • Semantic embeddings: compare meaning when wording differs beyond what string similarity captures.
  • Attribute and ensemble re-ranking: distinguish plausible candidates with supporting charge attributes as well as similarity.

A high top score alone is insufficient. If two candidates score 0.91 and 0.90, the leading candidate has little separation. The pipeline therefore checks both acceptance thresholds and the margin between competing candidates.

Documented default matching settings
SettingDefaultRole
Fuzzy threshold90String-similarity acceptance
Embedding threshold0.85Semantic candidate assessment
Re-ranking threshold0.85Combined-score acceptance
Minimum margin0.03Separation from the runner-up

These are configurable workflow thresholds, not probabilities of correctness. More permissive settings can reduce review volume while increasing incorrect automatic mappings.

Human review and output

Make the reason for a mapping inspectable.

Records that lack sufficient evidence or have close competing candidates are flagged for human review rather than forced into a category. A review flag is an intended outcome of the workflow, not automatically a pipeline failure.

Outputs retain the original code and description alongside the proposed standardized key, reference match, matching method, available scores and attributes, description-recovery status, and review flag. The diagnostic-upload edition produces a three-sheet intermediary workbook.

Keeping the input, evidence, and decision together supports review and correction without requiring users to inspect notebooks or pipeline code.

Validation

Watch incorrect confident matches, not only automation volume.

The documented validation approach compares results with previously reviewed mappings and examines automatic-match accuracy, auto-resolved versus review-required volume, incorrect high-confidence mappings, score distributions, and performance by jurisdiction and on unseen codes.

Schema differences, filename variation, missing historical descriptions, and threshold sensitivity remain practical limitations. Generalization to a new jurisdiction requires its own checks. The objective is consistent, traceable standardization with human oversight, rather than maximizing the fraction classified automatically.
